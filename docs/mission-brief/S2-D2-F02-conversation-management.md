## 1. Mission and user value

Give the Student and the specific Mentor who accepted that Student's Help Request a private, durable text conversation about that request. A conversation belongs to **one accepted Help Request**. Two accepted requests involving the same pair have two distinct conversations. The Student can move from an accepted request into chat; the Mentor can reach the same chat from accepted request context and an authorized conversation list. Both can read history and exchange messages in near real time without refresh. Chat may answer the question without any appointment.

This brief frames the complete F02 experience and its F01 integration. It does not reopen F01's selected-Mentor submission, Mentor-only decision, or `PENDING → ACCEPTED | REJECTED` lifecycle.

## 2. Actors and end-to-end journeys

| Actor | Intended journey and visible states |
| --- | --- |
| Student | Submit a request to a selected Mentor through F01; see `PENDING` without usable chat; after the Mentor accepts, find the request's conversation from accepted detail and/or an authorized list; open it, see request context and existing messages, send text, see the Mentor's persisted reply appear through a live listener, leave, and reopen with history intact. Initial loading, no conversations/messages, denied or lost access, failed subscription, and uncertain/failed send require truthful, recoverable states. |
| Mentor | Review a request addressed to their account in F01 and accept it; see the corresponding conversation available only after the integrated outcome is durable; find it through accepted request context and an authorized Mentor conversation list; read Student messages, reply, and see persisted updates. Pending/rejected requests do not yield chat. The same loading, empty, denied, subscription, and send-failure states apply. |
| Trusted backend and Firestore | F01 decides the request; F02 provisions exactly one matching conversation within the approved acceptance consistency boundary, persists messages, and enforces access. Firestore listeners deliver authorized changes. |

The interface should reuse HelpiNUS navigation, page, card, status, form, and responsive conventions. Desktop and mobile use, keyboard operation, readable focus/status feedback, and the project's WCAG 2.1 AA target require later verification. Exact chat layout and announcement behavior remain design/grilling decisions.

## 3. Confirmed scope and non-goals

**Confirmed from F02 specification and approved F01 artifacts:** Both roles have authorized conversation discovery and detail; accepted-request entry; request context; persisted chronological text history; sending by either participant; near-real-time listener updates; clear empty/loading/failure/denied states; session-safe listener cleanup; trusted parent and participant identities; no usable chat for pending/rejected requests; retries and races cannot create duplicate conversations. Runtime validation, Rules, service adapters, integration tests, and user/developer documentation are part of eventual delivery. A mock adapter can support isolated UI evidence but cannot prove production integration.

**Excluded:** Mentor availability, consultation slots, appointments or booking; request withdrawal, closure, reassignment, automatic rejection or a second decision state machine; public rooms and arbitrary direct messaging; notifications, attachments, voice/video, AI chat, read receipts, reactions, editing/deleting messages, unread counters, retention/deletion policy, or other advanced messaging unless separately approved. The shared Sprint 1 `CLOSED` symbol remains dormant for F01; F02 does not make closure operational. F01 plus F02 will not complete all Sprint 2 consultation/booking work.

## 4. Conversation lifecycle and governing invariants

1. F01 creates an immutable, specifically addressed request as `PENDING`; only its addressed Mentor with a currently eligible account can decide it. A later module or Mentor-profile change alone does not remove that decision authority. F01 owns status, decision, pending tuple key, and Student summary updates. F02 must not independently set request status.
2. A successful acceptance establishes exactly one conversation whose canonical parent is that **request ID**, with server-controlled Student and addressed Mentor IDs copied from the authoritative request. Repeated acceptance returns the same pair; another accepted request for the same pair gets a different conversation. No independent client or public creation path is permitted.
3. A pending or rejected request grants no usable conversation or message access. Rejection creates no conversation. If a nonaccepted request already has a deterministic conversation, F01's approved design fails closed for support investigation rather than deleting it or reporting success.
4. The final accepted transition and conversation creation must share one atomic outcome or an equivalently approved consistency protocol. No durable `ACCEPTED` request may be left without its required matching conversation. A failed provision leaves acceptance unconfirmed; a lost reply reconciles the durable pair without a second conversation. A corrupt accepted pair must fail closed rather than produce an apparently successful chat link.
5. Parent link and membership cannot be chosen, changed, or bypassed by clients. Request state and current participant eligibility must govern reads, writes, and listeners. Message identity, sender, body and authoritative creation time must be persisted; history must survive refresh and later sign-in.

The F01 **approved technical design** proposes `conversations/{helpRequestId}` and a transaction participant conceptually `provisionForAcceptedRequest(tx, {helpRequestId, studentId, mentorId, acceptedAt})`. That deterministic path and same-transaction integration are inherited F01 compatibility requirements for the current implementation, not a new F02 product choice. The precise F02 schema/helper implementation, message path and query strategy belong to later technical design. A departure that weakens the accepted-pair invariant would require explicit design reconciliation and approval.

## 5. Functional and real-time behavior

- **List and entry:** Both participants can find only their own accepted conversations. The list and accepted-request detail lead to the same per-request chat. The Mentor's accepted request view already exists; the Student's accepted detail exists but has no chat link. List order, preview metadata, handling of historical accepted records, and exact routes remain open.
- **Detail and context:** On opening, show the associated request context available to that participant, then its existing messages in stable chronological order. A loading state must not be mistaken for an empty history. Missing, corrupt, foreign, nonaccepted or revoked access must not expose stale private content.
- **Compose and send:** Both participants can submit valid nonblank text. The submitted sender is derived from authenticated identity and must equal the current participant. Invalid and oversized text is rejected authoritatively; exact length, whitespace normalization, retry identity and uncertain-send reconciliation remain open. Rendering must treat message text as text, not executable markup.
- **Synchronization and persistence:** Authorized Firestore listeners deliver newly persisted messages to both connected participants without manual refresh. Reopening or signing in later retrieves durable history. Stable ordering, timestamp ties, pagination and concurrent-send display behavior require later decisions. Listeners unsubscribe and discard late callbacks after route, service, account or eligibility changes; listener errors have distinct feedback and retry.
- **Responsive and accessible states:** Include no conversations, no messages, loading, list/detail failure, denied/lost permission, send in progress, uncertain/failed send and recovered state. A recoverable error must not be represented as a confirmed empty conversation or successful delivery.

## 7. Security and data integrity expectations

- The trusted identity is Firebase Auth plus authoritative `users/{uid}` role/status/email/verification. `ProtectedRoute` and local session state are navigation aids; Admin SDK provisioning must authorize explicitly because Rules do not apply to it. Account deactivation and eligibility changes must deny new protected operations and access according to the current account model; the precise historical chat experience and recovery copy require grilling.
- Direct conversation creation, update and deletion must remain denied to clients; only F01's authorized acceptance integration may provision. Parent request state, role-specific IDs and immutable membership must be checked for conversation/message gets, lists, listeners and writes. A forged participant array or arbitrary conversation ID cannot confer access.
- A message sender cannot be supplied as another user's UID. Direct Firestore send, if retained, needs Rules validation of actor, accepted parent, body and timestamp; a callable alternative would need equivalent trusted checks. Message updates/deletes remain outside scope. Retried sends and concurrent sends need a deliberate duplicate/order policy; no current F01 operation receipt automatically covers messages.
- Rules are not filters: a query/listener must prove access for its possible results, not rely on the documents currently present. Parent dependent reads, query limits, indexes, message subcollection access, and account revocation should be exercised against real client SDK/Emulator paths. Server-side list projections must enforce the same per-parent gate and bounded results.
- Unsubscribe and clear private UI state on sign-out, account switch, route unmount, detected denial or service swap. Discard callbacks and promises from the old session. Never show another participant's history or a stale composer after permission loss. Existing F01 session cleanup is reusable behavior, not proof that new chat listeners are safe.

## 8. Initial acceptance criteria (scope, not a test result)

1. The active addressed Mentor's successful F01 accept durably commits `ACCEPTED` and exactly one matching conversation for that request; provision failure commits neither, and retries/races cannot produce a duplicate or a false accepted result.
2. Separate accepted requests for the same Student/Mentor pair have separate conversations. Pending/rejected requests and arbitrary client-created documents grant no usable chat; anomalous parent/conversation pairs fail closed.
3. Student and Mentor can each find only authorized conversations, enter the same request-linked chat from accepted context, and see the correct parent question/module context and persisted prior messages.
4. Either participant can send valid text stored with their authenticated sender and authoritative time; invalid, blank or over-limit text is rejected under an approved policy. Concurrent or retried sends produce the approved ordering/duplicate outcome.
5. Both connected participants receive new persisted messages through authorized live listeners without refresh; history survives navigation, refresh and subsequent sign-in. List and history queries remain bounded and consistently ordered under the approved design.
6. Foreign, signed-out, wrong-role, inactive, unverified or otherwise ineligible users cannot list, subscribe, read or send. Clients cannot forge parent, membership, sender or server-controlled timestamps; direct message operations obey Rules.
7. Loading, empty, denied, subscription failure and uncertain-send UI states are truthful and recoverable. Account/route changes clear old private content and listeners. Desktop, mobile, keyboard and assistive-technology observations are recorded.
8. Real integrated Auth/Functions/Firestore/Rules Emulator tests and two-client browser evidence cover the accepted pair, live send/receive, persistence, hostile access, faults and races. Mock results are labeled separately, and the F01/F02 handoff reports outstanding RTT and release gates honestly.
