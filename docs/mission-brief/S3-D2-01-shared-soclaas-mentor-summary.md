## 1. Mission overview

Deliver the Phase 1 work in Sprint 3 requirement **S3-D2-01**: a server-side, reusable connection to the NUS School of Computing SoCLaaS gateway and a Mentor-invoked summary of an authorized, accepted Student–Mentor conversation. The Mentor should receive a consultation brief they can inspect and edit. Developer 1 owns **S3-D1-01**, the Student Study Assistant, and should be able to consume the shared gateway without importing Mentor prompt or conversation logic. Developer 2 owns the gateway proposal and Mentor feature, subject to shared-file ownership approval.

The development sequence is **A: restricted SoCLaaS connectivity**, **B: a controlled real-provider Mentor button and editable brief**, **C: production-path readiness**, **D: S3-D2-02 adversarial security hardening**, then **E: further quality refinement and release preparation**. A and B are early Phase 1 milestones; C completes Phase 1. B is permitted only for designated test identities and synthetic conversations in an isolated development/staging Firebase project. The callable may be technically reachable during B, so the backend must deny everyone outside that test scope. Full distributed quotas are not a prerequisite for B; essential identity, conversation, privacy, and bounded test-resource controls are. C establishes production-path technical readiness; production release to real users waits for successful D adversarial security verification. D is the next major mission after Phase 1, and detailed summary-quality work follows it.

## 3. Phase 1 in-scope requirements

### Functional and integration

1. **S3-D2-01 / shared gateway:** Establish a configurable server-side SoCLaaS client using a model permitted for the project's key. Provide one small provider interface and a mock with the same observable success/failure shape, so **S3-D1-01** and the Mentor handler can be built and tested independently.
2. **S3-D2-01 / Mentor request:** Let a Mentor select an accepted conversation and explicitly request a fresh consultation brief. The client sends an identifier, never message bodies, participant identities, arbitrary Firestore paths, prompt instructions, or provider credentials as authority.
3. **S3-D2-01 / trusted retrieval:** Before the provider call, authenticate the Mentor, verify current eligibility, re-read the accepted help request and matching conversation, confirm the addressed `mentorId`, and retrieve only messages from that authorized conversation in deterministic order within an approved bound. Validate each retrieved message's schema, sender against the accepted pair, and text bounds before prompt construction; define a fail/omit policy for corrupt records. Missing, corrupt, revoked, empty, and overlong histories need defined outcomes.
4. **S3-D2-01 / brief:** Produce a bounded, validated, editable draft with conversation summary/main discussion points, unresolved Student questions, suggested teaching approaches, and limitations or missing context where appropriate. The initial trusted context/system prompt must specify this structure, factual grounding, and the untrusted status of stored messages. Expose loading, success, timeout, quota, malformed-response, and other safe failure states. The Mentor controls any subsequent use; no AI result is sent as a message or used to mutate bookings, appointments, requests, or other business state.
5. **S3-D1-01 coordination:** Preserve the existing Student callable seam unless Developer 1 approves a change. Provide the shared gateway contract, configuration ownership, errors, and mock provider early enough for Developer 1 to integrate the Student handler without coupling to Mentor code.

### Non-functional, security baseline, and testing

- Keep the SoCLaaS bearer key exclusively in a server-side approved secret mechanism. Separate dev/prod values and model configuration; restrict outbound requests to the approved HTTPS SoCLaaS origin with a safe redirect policy, and fail closed if configuration or model access is invalid. The AI callable must not return credentials, hidden instructions, or retrieved conversation bodies to the browser; the existing authorized chat UI continues to display its own messages. Do not place private prompts, conversation bodies, or secrets in test snapshots or routine logs.
- Enforce input/context/output bounds and deadlines from the first real-provider call. During controlled Milestone B, the backend restricts designated test identities, enforces a small total invocation cap across the deployed test scope and bounded concurrency, and denies other callers even if they can reach the callable; a frontend flag is insufficient. For production-path technical readiness in Milestone C, add approved per-user quotas, an aggregate limit that works across Function instances, and bounded retries only for appropriate transient failures. Account for in-flight concurrency and provider-side key limits; a process-local global counter alone is insufficient for either a cross-instance test cap or production quotas. Exact thresholds need evidence and approval.
- Treat stored messages as untrusted task data. The backend fixes scope and instructions; the model receives no privileged application-action tools. Validate the provider response, render it as inert text, and require human review. Log minimal structured outcome/usage metadata, with privacy and retention policy resolved in the PRD/TDD.
- Verify role denial, foreign-conversation denial before retrieval or provider invocation, accepted-pair and per-message integrity, bounding, malformed output, timeout/429/5xx handling, test-identity denial, invocation/concurrency caps, mock isolation, and UI states. Initial summary checks use a few synthetic conversations to confirm required sections, nonempty/bounded/parseable output, and obvious factual omissions or inventions. Milestone A uses a restricted server-side harness with synthetic input, approved key/model, basic bounds and a hard invocation cap. Milestone B additionally verifies the actual button → Firebase callable → authorized message retrieval → real SoCLaaS → editable brief path with designated test accounts and synthetic conversations only. An isolated development/staging Firebase project and backend restriction are mandatory; no real Student data or general application users may enter B. Milestone C adds and tests full distributed quotas and production-path controls for technical readiness; real-user release remains gated by D. Do not treat an unavailable credential or mock-only button as a passing real-provider milestone.
- Preserve existing conversation, auth, and Student feature behavior. Later checks should use focused unit/emulator/UI evidence and the repository's `npm run check` and app-verification workflow where applicable.

## 6. Security and trust boundaries

The client controls only the invocation and selected identifier. Firebase Auth and the authoritative `users/{uid}` record establish the requester and role. The callable must check the accepted help request and exact conversation pair before any message query; Admin SDK access bypasses Rules. The server selects a bounded slice, validates each message and its sender, records whether history was omitted, and gives the model only that slice as untrusted data. Model output is untrusted display content and requires schema/size validation plus safe text rendering. SoCLaaS credentials and operational config stay on the server, and outbound traffic is restricted to the approved gateway origin. A read-only summariser receives no tools that send messages, read additional Firestore paths, or update persistent business state. The Mentor must review and explicitly take any later action. Access revocation during inference requires an explicit response-time recheck or an approved, documented revocation-delay policy.

Milestone A has no public callable. Milestone B may use a deployed, technically reachable callable only in an isolated development/staging Firebase project. Its backend must require designated test identities as well as current Mentor role and exact conversation authorization, enforce strict input/context/output/time bounds and a small total invocation cap across the deployed test scope with bounded concurrency, and use synthetic conversations only. Frontend feature flags do not establish this boundary. For production-path technical readiness in Milestone C, application-wide quotas need shared durable coordination across instances, with per-user enforcement and tested audit/error handling. No production traffic or real Student data belongs in A or B without separate approval.

This boundary is the Phase 1 safety floor. Phase 2 evaluates how stored malicious text can distort the summary or induce disclosures and whether these controls hold under adversarial tests; it may tighten prompts and validation without replacing the authorization architecture.

## 7. Initial summary objectives and later refinement

The Phase 1 consultation brief must contain **conversation summary/main discussion points, unresolved Student questions, suggested teaching approaches, and limitations or missing context where appropriate**. A proposed review format uses those four sections with concise, editable text and visible AI-draft labeling. The initial trusted context/system prompt must specify the structure, factual grounding in the selected messages, and that stored conversation text is untrusted data. Sparse, contradictory, or truncated context should be identified rather than filled with invented facts, answers, or commitments.

Phase 1 testing checks the required sections, nonempty and bounded content, parseability against the approved contract, and a small manual sanity review of synthetic examples for obvious inventions or omissions. Exact fields and limits belong in Grilling/PRD. LLM-as-judge, semantic similarity metrics, large quality datasets, complex scoring rubrics, and repeated prompt-tuning cycles are not Phase 1 gates. Detailed quality refinement comes after S3-D2-02 security testing and hardening.

## 9. Phase 1 acceptance criteria

1. **A:** A restricted server-side test harness proves controlled real connectivity to an approved SoCLaaS model from the intended Functions runtime with synthetic input, basic bounds, timeout, and a hard invocation cap. Its verified request path informs the shared adapter built in B1; the key never appears in client assets, responses, logs, or committed files. Missing config fails safely. The smoke test exposes no public callable.
2. The gateway is reusable and independently testable with Mentor and Student-shaped mock consumers; Developer 1 can integrate without importing Mentor modules. The Student production handler remains Developer 1's delivery obligation. Final proof that both production AI features use the same gateway is a joint S3-D1-01/S3-D2-01 integration gate and does not delay delivery of the shared interface to Developer 1.
3. Mentor role, accepted parent, exact conversation membership, and message sender/integrity are checked by trusted code before prompt construction. Tests show unauthenticated, Student, foreign Mentor, pending/rejected, and missing cases fail without provider invocation; corrupt records follow the approved fail/omit policy and never reach the provider as invalid data. The response-time access policy is tested.
4. Only bounded messages from the selected authorized conversation enter the model context, in a deterministic order. Truncation/empty behavior is explicit; client-supplied message text cannot expand scope.
5. **B:** A designated test Mentor in the isolated development/staging Firebase project can open an accepted synthetic conversation, click **Summarise Conversation**, invoke the Firebase callable and real SoCLaaS provider, then inspect and edit the returned brief. Its approved structured contract includes conversation summary/main discussion points, unresolved Student questions, suggested teaching approaches, and limitations or missing context where appropriate. The initial trusted prompt requires factual grounding and treats stored messages as untrusted data. Backend checks deny nondesignated identities even if they invoke the callable directly. Strict bounds, test-wide invocation and concurrency caps, safe rendering, and the no-action/human-review boundary are verified. No real Student data or general-user traffic is used.
6. **C:** Timeouts, 429/quota, transient failures, malformed output, and missing configuration produce safe, usable UI feedback. Approved per-user and multi-instance aggregate limits, operational concurrency controls, audit/error handling, and baseline-security tests pass for production-path technical readiness; real-user release remains gated by successful D adversarial security verification. Routine audit/log content excludes private message text and secrets.
7. Focused functional, emulator/integration, UI, regression, baseline-security, and controlled real-provider results are recorded. Initial output tests prove required sections plus nonempty, bounded, parseable responses; a small manual review of synthetic summaries flags obvious inventions or omissions. Developer 1's shared-contract tests remain compatible; any contract amendment is approved through the ownership process. Extensive semantic evaluation and optimization are not required for Phase 1. No claim of full Phase 2 security completion is made.
