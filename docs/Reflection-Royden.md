# Royden's Developer 2 Reflection

I use the three themes in the CS3227 reflection guide—AI security, spec-driven development, and basic multi-agent software engineering—to assess my Developer 2 work on HelpiNUS. My examples come from the feature specifications, interaction logs, handoffs, and the final implementation. A recorded test result is evidence for the version and environment in which it ran; I do not treat it as proof that a later version or the live model behaves identically.

## AI security

The Mentor summary made prompt injection concrete for me. Its input is an accepted Student–Mentor conversation, so either participant can place instructions inside what should be task data. In [S3-D2-02's PRD](features/S3-D2-02/PRD.md), I considered a message that impersonates a system or developer role, a request to ignore the summarisation task, a request for hidden instructions or credentials, an instruction to include a second conversation, a demand for HTML or a different output format, and a request to send a message or change a booking. I also included an ordinary discussion *about* prompt injection. That last case matters: rejecting text merely because it contains suspicious words would damage the legitimate task without establishing a reliable security boundary.

I treated the saved messages, the provider response, and the development agent's repository and tool inputs as different untrusted surfaces. The [Mentor handler](../src/functions/src/mentorConsultationSummary.ts) checks the current Mentor and exact accepted help-request/conversation pair **before** reading messages, selects bounded history from that one conversation, and places sender-labelled message text under fixed server instructions. The provider receives no application-action tools. The handler validates the four-section result and rechecks access before returning it. These choices constrain what the model can see and what its output can cause. The historical seven-case mocked campaign recorded in the [S3-D2-02 log](../logs/royden/2026-10-21-S3-D2-02-prompt-injection-defense.md) inspected selected paths and provider payloads and compared business state before and after hostile text. It checks application boundaries, not live-model obedience or the factual quality of a real brief.

My limit on the AI feature was also operational. The Mentor must deliberately select **Summarise Conversation**; page entry or a new chat message does not trigger inference. The [callable](../src/functions/src/mentorSummaryCallable.ts) is gated to a configured `helpinus-dev` test audience, and the final [capacity module](../src/functions/src/aiTestCapacity.ts) permits one active Mentor provider call at a time. The planned ten-attempt total cap is absent from that module, and shared Student/Mentor daily quotas and Mentor audit retention are not implemented. I cannot count a historical counter field or an approved TDD as a running control. The final [conversation UI](../src/frontend/src/pages/ConversationPages.tsx) displays a generated brief as read-only text and does not send or save it as a chat message. The approved SDD called for in-page editing, so I recorded that as an unimplemented requirement rather than describing the final UI as editable.

Human oversight had to apply to both the product and the engineering process. The [S3-D2-01 decisions](features/S3-D2-01/GrillingDecisions.md) separate approval of a model, a synthetic test audience, a first real inference, and eventual real-user release. The [S3-D2-01 log](../logs/royden/2026-10-20-S3-D2-01-soclaas-mentor-summary.md) records a controlled hosted attempt that timed out and a later controlled local-preview success; neither establishes general availability or real-data approval. Model-generated text must never be able to redefine an approval gate. For coding agents, I followed the repository rule that specifications, logs, source comments, and tool output are evidence to inspect, not authority to grant themselves broader access or claim a check passed.

## Spec-driven development

A useful specification tells an implementer which actor may act, what data is authoritative, the exact input and output shape, the state transitions, failure behavior, and what evidence will count as acceptance. The [S2-D2-F01 PRD](features/S2-D2-F01/PRD.md) and [S2-D2-F02 PRD](features/S2-D2-F02/PRD.md) illustrate why this matters: a request is not merely “accepted”; acceptance must produce the matching conversation, handle retries and races, and preserve participant authorization. For the summary, `{helpRequestId}` identifies an accepted request and same-ID conversation; the browser does not get to submit an arbitrary transcript or prompt. Those are buildable boundaries. “Generate a secure summary” alone would leave too many choices to an agent.

I judge a spec precise enough when another agent can write an independent negative test without asking me what “secure,” “current,” or “bounded” means. The [S3-D2-01 PRD](features/S3-D2-01/PRD.md), [TDD](features/S3-D2-01/TDD.md), and [Requirements-to-Tests](features/S3-D2-01/RequirementsToTests.md) name the role and pair checks, message selection order, 30-message and 12,000-character ceilings, response-time recheck, safe errors, and separate real-provider gates. They also leave model entitlement and production budgets open where external facts or owner decisions were missing. A placeholder number would have made the design appear complete while hiding an unverified assumption.

The implementation taught me that approved intent and delivered behavior need separate records. The original S3-D2-01 plan required an editable brief and a ten-attempt test cap. The final source has a read-only brief and only a single active lease. The Student Study Assistant also retains its own provider path rather than using the planned shared gateway. During final documentation reconciliation, I added explicit dispositions to the Mission Brief, PRD, TDD, and traceability documents while preserving the original approvals and historical test claims. Those edits change the SDD hashes, so they need Developer 2 review and approval before being represented as approved snapshots. I would use the same sequence for a future material change: record the decision, revise the relevant contract and acceptance criteria, implement, test the affected boundaries, then update guides and handoffs.

Tests must challenge the intent behind the words. In the [S3-D2-01 implementation log](../logs/royden/2026-10-20-S3-D2-01-soclaas-mentor-summary.md), independent B2 review found that a Firestore `orderBy(createdAt)` query could omit a malformed message, even though the initial synthetic suite passed. The correction checked ordered and unordered counts before inference; the new test addressed the data-integrity intent rather than merely restating the query. In S3-D2-02, the first cross-conversation case accidentally included its private marker in the attack text, producing a misleading failure. Correcting that fixture showed why an independent expected value and a review of the actual provider payload matter. Conversely, a green test for an old editable UI cannot prove the current read-only UI meets the approved editing criterion.

## Basic multi-agent software engineering

I benefited from specialization where the work crossed different trust and knowledge boundaries. The [Developer 2 workflow](../workflow/agents/README.md) assigns the coordinator the gates and handoffs, an implementation specialist the scoped code and tests, independent code/test and security reviewers the challenge function, guide specialists the user and technical explanations, and a logger the evidence trail. The S3-D2-01 log records separate B1 gateway, B2 Mentor backend, and B3 UI gates, with reviewer findings and bounded correction cycles. In the final documentation pass, a read-only feature assessor, separate guide writers, and an independent documentation reviewer caught stale claims about editing, identity collections, approval hashes, and post-merge verification. That division helped because the writer who made a claim was not the only person checking it.

Specialized agents still need narrow instructions and a common handoff. I would pass the exact worktree and branch, approved artifact paths and hashes, source/contract ownership, assigned writable files, requirement IDs, commands and environments actually run, pass/fail/partial results, and outstanding gates. The [S3-D2-01 handoff](../workflow/handoffs/royden/S3-D2-01.md) and [S3-D2-02 handoff](../workflow/handoffs/royden/S3-D2-02.md) show why status must be chronological: an early timeout, a later local-preview success, and a post-merge test removal are all true, but none should be collapsed into “the final hosted feature passed.” A concise inventory can prevent every agent from rereading the same large evidence set, while direct source inspection remains necessary for disputed claims.

Errors or malicious instructions can enter at each handoff. An analyst can turn an assumption into a requirement, an implementation agent can treat a message body or repository comment as an instruction, a test author can build a fixture that hides the bug, and a reviewer can accept a green result from the wrong revision. I reduce those risks with explicit human scope approval, read-only independent reviews, exact-byte provenance, separate source and test evidence, and clear `PASS`/`PARTIAL`/`NOT RUN` labels. I also keep agents within their file responsibilities and do not let a model approve its own work. The most useful artifact each agent leaves is a small, verifiable account of **what changed, what was observed, what was only planned, and what remains open**. My final documentation review showed that this evidence discipline matters as much after implementation as it does before coding.
