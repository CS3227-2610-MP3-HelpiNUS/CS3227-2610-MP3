These are current facts, not delivered AI behavior. The local `Dev2-local-SDD` tree is the unversioned drafting location under `workflow/agents/README.md`; approved bytes are published to the feature worktree only through its later approval/hash/ledger process. Live remote freshness is unverified.

Design constraints: one read-only, explicitly invoked Mentor summariser; no tools, automatic messages, business-state writes, saved drafts, arbitrary transcript input, or general search. The shared gateway knows provider transport and resource controls, not Mentor authorization or Student prompt rules. Structured-output checks establish shape and bounds; a few synthetic human reviews check obvious inventions or omissions. No LLM judge, semantic score, or large prompt-quality suite is introduced in Phase 1.

Time and HTTP are genuine variable seams. Firestore emulator state is used for authorization and quota tests rather than mocking internal query helpers. ## 3. Contract, errors, and state visible to the Mentor

All four brief properties are required, plain-text, trimmed, nonempty strings. The sum of Unicode character counts is at most 8,000; each field is also bounded by that total. `unresolvedQuestions` and `limitations` may explicitly say that none were identified **from the selected messages**. The trusted instruction requests a **bare JSON object** with the four approved fields, without Markdown fences or additional commentary, and forbids inventing a question, limitation, fact, answer, commitment, or Student intent to fill a required field. A validator checks structure and size, not semantic truth; the small manual synthetic review supplies the latter sanity check. Parse exactly one JSON object, require exactly the four named string properties, reject missing/extra/wrong-type/empty/oversized values, and never use raw malformed text as the brief. Do not assume SoCLaaS/model support for enforced JSON output; use a provider-specific enforcement option only after compatibility with the selected model is confirmed. The UI keeps original generated text editable in memory only and renders with text nodes/textarea values, not HTML interpretation.

The response intentionally contains no message bodies, provider request, model prompt, secret, audit ID, or operational internals. `partialHistory` is computed by the server from selection, not by the model. In an empty accepted conversation the handler returns a distinct safe `EMPTY_HISTORY` outcome without provider invocation; the UI shows an empty state instead of four fabricated fields. The transport can use a stable `HttpsError` reason in safe `details` while retaining the existing callable wrapper. Specific safe mapping:

| Cause | Callable code / safe reason | Mentor behavior |
| --- | --- | --- |
| Missing Auth | `unauthenticated` | Sign-in guidance. |
| Ineligible role, foreign/missing/inconsistent pair, or revoked access | `permission-denied` / `ACCESS_UNAVAILABLE` | Access unavailable; discard draft. Do not reveal whether a foreign ID exists. |
| Selected corrupt message or matching record integrity failure | `failed-precondition` / `SUPPORT_NEEDED` | Support-needed state; no inference. |
| Empty selected history | `failed-precondition` / `EMPTY_HISTORY` | Empty conversation state; no inference. |
| B3 cap, C daily budget, or in-flight ceiling | `resource-exhausted` / `AI_CAPACITY` | Temporary capacity message; no provider call. |
| Missing/unapproved secret, model, origin, or deployment gate | `unavailable` / `AI_CONFIG` | AI unavailable; no raw config values. |
| Provider deadline or transport uncertainty | `deadline-exceeded` / `AI_TIMEOUT` or `unavailable` / `AI_PROVIDER` | Retry guidance that does not promise a free attempt. |
| Rejected/rate-limited response | `resource-exhausted` / `AI_PROVIDER_LIMIT` | Provider temporarily unavailable; no raw body. |
| Invalid/oversized provider response or invalid brief JSON | `unavailable` / `AI_RESPONSE` | No successful brief; safe retry guidance. |

The existing generic `mapError` logs arbitrary thrown errors. AI paths must convert provider failures to sanitized typed errors before that logger; if necessary, alter the wrapper after shared-owner approval so it logs only safe code/feature/correlation metadata. Never forward raw HTTP response bodies, `Authorization` headers, full prompts, message text, generated output, or stack traces containing them to client or routine logs. Unexpected faults still return a generic safe error. Error mapping is part of the gateway/handler contract and mock parity tests.

## 4. Success data flow and trust boundaries

1. A Mentor action passes only `helpRequestId` through the typed service callable. Strict Zod parsing rejects other keys and malformed IDs. The backend feature gate first verifies B3 project and exact designated UID in B, or the later approved release gate for real users. A frontend flag is only presentation. No provider or message read occurs for a denied test identity.
2. The handler uses `requireCurrentMentor` (Firebase Auth, current `users/{uid}` role/status/email, Auth user validity) and reads `helpRequests/{helpRequestId}` plus `conversations/{helpRequestId}`. It validates the parent as `ACCEPTED`, its `mentorId` equals the caller, both participant IDs match the same-ID conversation, and the stored conversation shape/timestamps match the existing F02 invariant. Missing/foreign/pending/rejected/mismatch fails before querying `messages`. Reuse the F02 pair validator where safe; avoid weaker parallel rules. Admin SDK does not inherit Firestore Rules.
3. The server queries only `conversations/{helpRequestId}/messages`, newest first by `createdAt` with document-ID tie break, bounded to one extra row beyond the 30-message ceiling. It walks newest complete messages until adding the next would exceed **30 messages or 12,000 total body characters**, or the lower approved model-specific context allowance. Before including or size-skipping a row within that selected walk, it validates the F02 stored schema, exact body normalization, expected fields/timestamps, and sender in the accepted Student/Mentor pair. A corrupt or unexpected-sender row encountered in the selected walk stops with `SUPPORT_NEEDED` before inference; the extra sentinel row is only evidence of omission and is not included. The extra row or a stopped bound marks `partialHistory`; selected rows are then sent in chronological order with deterministic tie break. No client-paginated cache or client-supplied text is trusted. Empty history ends without inference. The model-specific allowance covers serialized role labels, JSON framing, trusted instruction, output reserve, and provider context window; if the approved model's limits cannot be verified or calculated conservatively, the real-provider path fails closed. Bound serialized bytes as well as character counts.
4. The handler constructs one fixed trusted instruction requesting a bare four-field JSON object without fences or commentary, factual grounding, explicit uncertainty or “none identified” when supported, and refusal to follow instructions embedded in stored messages. A separate delimited data message contains only the selected sender role, order, and text. The model receives no tools, Firestore paths, secret, participant email, or hidden application authority. Stored messages are untrusted even though they passed structural validation.
5. The gateway validates configuration and bounded input first. The shared capacity module then reserves an attempt before any SoCLaaS inference request. The gateway sends plain HTTPS chat completions to the approved fixed origin and exact approved model, with `redirect: error`, a total deadline, response byte cap, and allowed output-token ceiling. It requires a successful status, exactly one returned choice with string `message.content`, no tool-call result, and nonnegative numeric usage if supplied; otherwise it reports `AI_RESPONSE`. Response reading aborts at the byte cap. It never uses `/responses`, provider tools, or arbitrary URLs. At C it may retry once after an explicit 429 rejection with admissible `Retry-After`, sufficient remaining deadline, and a new quota attempt reservation; 5xx, transport interruption, timeout, or an ambiguous sent request is not automatically resent. B3 can simply return the safe failure without retry.
6. The Mentor handler parses the four-field JSON, validates size/types, then immediately rechecks current Mentor eligibility, accepted parent, and exact conversation pair before return. If access changed, it discards the paid result. The response contains only the brief and `partialHistory`. The frontend checks its current UID/helpRequestId generation before installing the result; edits stay in page state and are cleared on account/conversation change. Generation never calls `sendMessage`, updates F01/F02 records, or saves edits.

The provider may have observed selected synthetic text even if a later access recheck fails; response-time recheck prevents delivery of the generated brief, not retroactive provider transmission. The security gate therefore requires pre-inference authorization and synthetic-only A–C data. Message changes during inference do not silently expand the selected snapshot: one invocation summarises the selected bounded slice at retrieval time; a later explicit click requests a fresh slice. Revocation of the authorized relationship is still rechecked before return.

## 5. Resource control and recovery

### A — restricted connectivity proof

Before A, an operator verifies the actual isolated project, Firebase-managed project secret, exact key-visible `/models` result, approved model ID/context/output limits, and approved HTTPS origin. **Selected mechanism:** one temporary, IAM-restricted operator-only HTTPS Function in the existing Node 22 Functions package/project, using the existing Firebase secret binding and backend-only Firestore for the one-attempt marker. It is not an `onCall` export or general-user route; verify invoker restriction before any catalog or inference request, and remove the temporary export after A evidence is captured. This is one small smoke entry, not a new service or generalized harness. If the project already has a simpler private operator execution path in the same Functions runtime with the same secret and durable marker, use that path instead and record the choice. The smoke entry reads the catalog first; only after Developer 2 approves an exact returned ID may it make one small synthetic inference attempt. The marker is consumed before sending, so a crash or uncertain response does not permit an automatic second attempt. Only an explicit recorded operator reset restores the cap. An unauthorized origin, unsafe redirect, missing configuration, or unsupported model stops without inference. If IAM, secret binding, or project isolation cannot be verified, A remains blocked rather than exposing a public callable. Evidence records operator, project identifier, catalog/model decision, timestamp, redacted result/status and count, never key/prompt body.

### B3 — bounded deployed test scope

An approved exact UID allowlist and verified synthetic-only project are deployment configuration, not client data. The backend denies other identities even on direct callable invocation. A backend-only Firestore transaction owns one test-scope counter and one active reservation: `attemptsUsed` begins at zero and is never decremented; each provider attempt increments it before network I/O and fails when already 10, making attempt 11 impossible across instances/redeploys. An active reservation serializes provider calls to **one in flight**. It holds a unique internal lease ID, start/deadline, and owner UID; release uses a transaction that only clears the matching lease. If the process crashes, the reservation expires only after the configured Function maximum execution time plus a safety margin; the HTTP deadline is shorter than that lifetime, so expiry cannot overlap a still-permitted provider call. A stale lease is reclaimed transactionally; a failed reservation never invokes the provider. The explicit operator reset is recorded and requires verification that no live call remains. Missing/invalid state fails closed. This B3 counter is sufficient for the early real-provider happy path; full C quotas are **not** a B3 prerequisite.

### C — common Student/Mentor budgets

Developer 2 extends the same admission concept into one durable shared budget scope used by both handlers. A persistent global concurrency document, one aggregate budget document for the approved window, a persistent per-UID active-lease document, and that UID's budget document for the same window are read and updated in one Firestore transaction for every provider attempt. The global document has a bounded map of active leases; the user active-lease document allows only one logical call. The window documents count request attempts and conservative token reservations. The approved per-user/aggregate thresholds and aggregate in-flight ceiling are checked before incrementing. A retry consumes another attempt but remains under the same logical user's active lease. Reserving a conservative token upper bound before each attempt protects the verified provider token budget; usage actuals are recorded separately, and missing usage never counts as zero. The budget-window key/reset rule must be approved from the verified key budget before C; no threshold or reset time zone is invented here. Persistent active leases prevent a day/window rollover from admitting overlap with prior-window calls. Firestore's transaction contention and document-size feasibility must be verified against the approved ceiling; if they fail, revise this shared module through owner review before C, without weakening atomic admission.

Reservations are held across the network call and released in `finally` by lease ID. A crash can conservatively consume daily capacity; it must not refund an uncertain provider attempt. Lease expiry follows the same hard-runtime/deadline ordering as B3 and is transactionally pruned before a new admission. An explicit negative test proves a timed-out invocation cannot continue provider work after its lease is reclaimable. If Firestore admission/release is unavailable, fail closed for new calls, retain consumed counts, and emit sanitized operational evidence. No process-local count is a safety authority. There is no client operation ID or exactly-once charge claim; a lost callable response can cause a new user-initiated attempt. UI copy must not promise that the previous attempt was free.

## 6. Audit, configuration, and privacy

At C, a backend-only `aiAuditEvents/{generatedId}` record for an authenticated AI invocation has `actorId`, `feature` (`STUDENT_STUDY_ASSIST` or `MENTOR_CONSULTATION_SUMMARY`), `createdAt`, `expiresAt` (30 days later), `outcome`/safe error class, approved model ID when known, attempt count, and usage when available. Denied admission, failure, and success are distinguishable. An unauthenticated rejection has no trustworthy actor ID, so it emits only a content-free operational denial metric and never fabricates an audit actor. No prompt hash, raw prompt, message body, generated text, bearer key, provider body, or participant name is stored. Firestore Rules continue to deny client reads/writes. Amend the shared scaffold schema only after Developer 1 approval. Configure and verify a backend retention mechanism for the 30-day expiry; a timestamp field alone is insufficient, and an eventually deleting TTL policy must be assessed against the approved retention interpretation before claiming AC-36. Audit-write failure must not turn a denied request into an allowed provider call; before C, select and test a fail-closed/operational-alert policy so required outcome records are not silently lost. A provider-paid success whose outcome cannot be audited is returned as a safe failure, with no refund claim. Routine logs contain only safe code, feature, time, and correlation metadata.

Server config is deployment-specific and validated at startup/use: Firebase-managed bearer secret with distinct dev/prod values, fixed approved HTTPS origin, exact approved model ID, verified model context/output limits, deadline and response-size limits, B3 project/UID gate, and later C budget values. `helpinus-dev` in `.firebaserc` is an alias, not evidence of isolation. Missing or invalid configuration yields `AI_CONFIG` before a provider inference. The frontend receives no configuration except a non-authoritative availability presentation flag. No example model name, UID, key allowance, numeric C quota, or provider retention claim is assumed.

## 7. Test seams and verification plan

The approved public seams are: (1) typed Mentor callable/handler observed through safe response and errors, with real Firestore emulator documents; (2) shared gateway `generate` observed by Student-shaped and Mentor-shaped trusted consumers, substituting only the actual HTTP provider adapter; (3) common capacity module observed through admitted/denied provider attempts against emulator Firestore, with controlled time for lease expiry; and (4) existing `HelpiNUSServices.callables.invoke` in the Mentor page, with deterministic callable fixture. Tests do not call private prompt helpers, mock pair-validation internals, or derive expected JSON by running production parsing logic. Provider test doubles capture bounded outbound requests without storing private real messages. Synthetic fixtures cover an explicit no-question/no-limitation result, sparse context, malformed records, same-timestamp ordering, cap boundaries, window rollover, and late revocation.

PRD coverage in this design: FR-01 maps to §5 A; FR-02/FR-03 to §2; FR-04/FR-05/FR-06/FR-07/FR-08 to §§2–4; FR-09 to §5 B3; FR-10 to §§3–5; FR-11 to §5 C; FR-12 to §6; FR-13 to §§1, 7–8. NFR-01/NFR-02 map to §§4–6; NFR-03/NFR-04 to §§3–4; NFR-05 to §§2–3, 7; NFR-06/NFR-07 to §§2, 7–8; NFR-08 to §§1, 3, 7. This is design coverage, not the deferred Requirements-to-Tests checklist or a claim that AC-01–AC-39 passed.

After separate implementation authorization, work can proceed vertically: A restricted one-attempt smoke path; B1 one gateway success/error with real/mock parity; B2 one authorized synthetic conversation then denial/integrity/boundary cases; B3 actual designated Mentor button-to-real-provider editable brief; C one shared-budget admission followed by cross-instance races, retries, audit, and both-handler integration. Each cycle begins with one failing behavior test at an approved seam, minimum implementation, then the next case. The Requirements-to-Tests artifact maps all FR-01–FR-13, NFR-01–NFR-08, and AC-01–AC-39; this TDD does not create it. Controlled A and B3 real-provider evidence cannot be replaced by mock results.

Verification for A–C must include focused unit/mock tests, Firebase emulator authorization and quota tests, Student contract compatibility, UI keyboard/responsive and stale-context checks, safe-log inspection, baseline security cases, and a small human sanity review of synthetic briefs for obvious factual errors. Run the repository's focused lint/type/unit checks and required `npm run check`/`verify:app` workflow during later implementation, recording actual commands, environment, results, and limitations. The D handoff carries selected-context rules, prompts, model/version, parser, quota/audit design, and attack surfaces for stored prompt injection, cross-user leakage, revocation, output manipulation, and unauthorized actions. Passing baseline tests does not claim D completion.
