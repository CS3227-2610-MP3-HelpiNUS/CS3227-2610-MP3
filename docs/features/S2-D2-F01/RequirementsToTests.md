## 1. Test contract and fixtures

**Case syntax:** Each numbered row gives a stable ID, PRD FR/NFR/AC and approved GD references, objective, preconditions/fixtures, action/input, observable result, persisted invariant, level/framework, evidence class and blocker. `E` means Firebase Auth/Functions/Firestore or Rules Emulator with real Firestore transactions; `M` means deterministic mock; `I` means integrated F01/F02 with real F02 helper and Rules; `H` means human browser/source review. “No writes” means compare before/after request, tuple key, operation receipt, Student summary and deterministic conversation document as applicable. Automated results must record command, environment, fixture IDs and pass/fail; manual results must record browser, viewport, observations and defects. Rows are test plans, not results.

Fixtures use `studentA`, `studentB`, `mentorA`, `mentorB`, a verified active Student/Mentor user and Auth record with matching email, a supported active catalogue module `moduleA`, `moduleB` not supported by `mentorA`, an inactive and missing module, active/inactive/missing Mentor profiles, and distinct fixed UUIDs `opA`/`opB`. Seed requests with controlled `createdAt` and document IDs to test ties, plus genuine server transaction timestamps for transition tests. Use fake timers only for UI scheduling; use barriers or controlled transaction faults for races, never sleeps. Keep user snapshots, request documents, receipts, tuple keys, summaries and conversations available to an Admin test reader. Rules tests use explicit verified claims and a client SDK; the synthetic Functions Emulator identity exception must not be assumed by Rules.

**Shared verification dependencies:** Developer 1 ownership authorization is recorded in TDD §16 and no per-file approval is needed. Execution still needs separate implementation authorization, a reviewed implementation parent, an F01 callable/Firestore Emulator harness with resettable collections and controlled fault/barrier hooks, request query indexes and actual listener harness, and F02's approved plan plus transaction-compatible provision helper, conversation schema/Rules/query and route for `I` cases. These technical/planning dependencies are not test passes. The proposed F01 wire `operationId` needs coordinated shared schemas, callers, proxy/mocks and contract tests; the existing `createHelpRequest.requestId` UUID is an operation token, not `helpRequests/{id}`. Inventory additional consumers at implementation time.
