## 1. Evidence contract and fixtures

Each `F02-TC-nnn` case is a separately reportable requirement-level check. Record the actual test reference, command, Node/emulator/browser version, fixture IDs, result, relevant before/after Firestore snapshots or UI observation, evidence location, status, missing evidence class and remediation owner in the feature ledger. `PASS` requires **all** assertions and evidence classes named in the row. `FAIL` means an executed assertion failed; `PARTIAL` means some required evidence passed but other evidence is missing; `BLOCKED` means a genuine documented dependency prevents execution; `NOT RUN` means executable but unexecuted. A mock result never substitutes for Emulator, real F01/F02, two-client live, CI or human observations. This draft records no case as passed or blocked.

Evidence classes: **U** pure contract/handler unit test; **M** deterministic service/component/router test; **E** authenticated Functions/Firestore Emulator with real transactions and Admin snapshots; **R** actual client SDK query/get/listener or hostile write under Security Rules Emulator; **I** production-wired F01/F02 acceptance path with real F02 helper, persistence and Rules; **L** two eligible client sessions observing actual live subscriptions; **H** human browser/keyboard/screen-reader, audit or document inspection; **C** Node 22 CI at an identified commit. A case may require several classes; list each outcome separately. Faults use controlled transaction/callable barriers or deferred responses, never timing sleeps.

Use synthetic `studentA`, `studentB`, `mentorA`, `mentorB` with matching Auth and `users` records, current verified email, correct active roles, and separate inactive, disabled, unverified, stale-email and wrong-role variants. Seed valid `PENDING`, `ACCEPTED`, `REJECTED`, missing-parent, mismatched-parent, malformed-timestamp and alternate-ID fixtures; preserve exact request/key/summary/conversation snapshots for negative paths. Acceptance fixtures use F01's real request and decision callables. Use two distinct accepted requests for the same pair. For paging, seed over 20 accepted requests and over 40 messages, equal native Firestore timestamps with distinct document IDs, older sender messages, foreign records and corrupt pairs. Use a fixed fixture clock only where equality/order is tested; transaction timestamps must be real server-side values for acceptance and send. Reset Auth and Firestore between independent cases. Client SDK Rules tests need explicit current claims; the Functions Emulator synthetic identity exception does not prove Rules authorization.

The test seams are the TDD-approved public interfaces: production `respondToHelpRequest` with the real F02 provision helper; authenticated `sendMessage` and `acknowledgeMessage`; actual owner-scoped request queries and conversation/message reads under Rules; `HelpiNUSServices.conversations` through Firebase and deterministic mock adapters; and the Student/Mentor pages. Do not make private hooks or transaction internals the acceptance seam. Proposed test homes are shared contract tests, `src/functions` handler/integration and Rules suites, and `src/frontend/src/test` service/route/page tests; exact filenames are assigned during implementation. An Admin reader may inspect persistence but must not stand in for a client authorization test.
